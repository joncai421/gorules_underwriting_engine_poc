# Headless Underwriting Engine PoC (PRD v2 — Multi-Stage Pipeline)

A working monorepo Proof of Concept demonstrating the modernization of an insurance
underwriting system from a **legacy hardcoded Spring Boot (Java 17)** service to a
**headless GoRules engine (TypeScript + `@gorules/zen-engine`)**: automated migration
and shadow-mode parity tooling, Excel rule-table import, 1-click rule onboarding with
hot-reload, and a pluggable **AI Copilot** for referral / evidence-request cases.

> See [`docs/requirement_PRD_v2.md`](docs/requirement_PRD_v2.md) for the full PRD
> (and `docs/initial_requirements.md` for the v1 baseline).

## The Underwriter pipeline (4 stages, 6 terminal dispositions)

```text
[1. Proposal Form Received]
        |
        v
[0. Derived Metrics & Formulas]      GoRules expressionNode
        bmi = round(weightKg / (heightCm/100)^2, 1), incomeMultiple = round(SA / income, 1)
        |
        v
<Sufficient Information?>            collect decision table (1.1 evidence rules)
   +-- NO  -> [1.1 Request For Additional Info] -> AI Copilot Mode A drafts the evidence request
   +-- YES
        v
[2. Risk Assessment]                 collect decision table: 12 RA_* rules, EM debits,
        |                             exclusions, decline/postpone/comorbidity flags
        v
[3. Risk Classification]             first-hit decision table: buckets total EM debits +
        |                             flags into STANDARD / TABLE_A / TABLE_B / TABLE_D / ...
        v
[4. Underwriting Decision]           formatter functionNode -> canonical envelope
   ACCEPT_AS_PER_APPLICATION | ACCEPT_WITH_LOADING (+25/50/100%) | ACCEPT_WITH_EXCLUSIONS
   | POSTPONE | DECLINE | REQUEST_ADDITIONAL_INFO   (isUncleanReferral -> AI Copilot Mode B)
```

## Prerequisites

- **Node.js 18+** (tested on Node 24) and npm.
- **Java 17** on `PATH` (or `JAVA_HOME`) — only needed for the legacy service; the bundled
  **Maven Wrapper** downloads Maven itself on first run. No global Maven required.
- Network access on first build for `npm install` and the Maven Wrapper.

## Quickstart

```bash
npm install                          # 1) all workspace deps (repo root)
npm run gen:xlsx                     # 2) create shared/sample-rules-upload.xlsx
cd legacy-java-service && ./mvnw spring-boot:run    # 3) legacy baseline on :8080
npm run engine                       # 4) GoRules TS engine on :3001 (another terminal)
npm run ui                           # 5) Admin UI on :5173 (another terminal; proxies /api)
```

`npm run dev` starts engine + UI together.

## Verification checklist (PRD v2 section 7)

```bash
npm run selftest       # 12 cases x {v1, v2} evaluated against the expected envelopes
npm run migrate        # regenerate v1 JDM from the legacy Java source (deterministic AST/regex)
                       #   - `npm run migrate:llm` prints the LLM migration prompt + schema instead
npm run verify-parity  # shadow mode: Java :8080 vs TS :3001 over all 12 cases (exit 1 on diff)
npm run build          # Admin UI type-check + production bundle (zero errors)
```

Expected: `Self-test PASSED (24/24)`, `PARITY PASSED: 100% (12/12)`, `✓ built`.

Parity compares, per case: `derivedMetrics` (bmi, incomeMultiple), `step1SufficientInfo`
(sufficiency + missing doc codes), `totalEmDebits`, matched rule order, `riskClass`,
`finalDecision`, and `loadingPct` — the legacy Java service implements the identical
four-stage logic (collect semantics in stages 1/2, first-hit chain in stage 3/4).

## API surface (GoRules TS engine, :3001)

| Method | Path                       | Purpose |
|--------|----------------------------|---------|
| GET    | `/api/rules`               | List rule versions + active id |
| GET    | `/api/rules/:id`           | Raw JDM JSON (for the editor) |
| PUT    | `/api/rules/:id`           | Save JDM + hot-reload (`?activate=true`) |
| POST   | `/api/rules/:id/activate`  | Switch active version |
| POST   | `/api/rules/onboard`       | Append stage-2 rules into a new version (1-click onboarding) |
| POST   | `/api/rules/upload-excel`  | `{ fileName, base64 }` -> parse `.xlsx` into the stage-2 table, return updated JDM |
| POST   | `/api/underwrite`          | Evaluate the 4-stage pipeline (`?aiAssist=true|false`, `?rule=<id>`) |

Legacy Java (`:8080`): `POST /api/legacy/underwrite` (same envelope, no trace/AI fields).

### Example

```bash
curl -s -X POST "http://localhost:3001/api/underwrite?aiAssist=true" \
  -H "content-type: application/json" \
  -d @- <<'JSON'
{"applicantId":"APP-2004","age":46,"heightCm":172,"weightKg":88,"smoker":false,
 "systolicBp":148,"annualIncome":80000,"sumAssured":1200000,"occupationClass":2,
 "recentSurgeryMonthsAgo":0,"medicalConditions":["FATTY_LIVER"],
 "submittedDocuments":["PROPOSAL_FORM","BLOOD_PROFILE"],"avocations":[]}
JSON
```

Returns the stage-by-stage envelope (`derivedMetrics`, `step1SufficientInfo`,
`step2RiskAssessment`, `step3RiskClassification`, `step4UnderwritingDecision`),
`executionTimeMs`, the GoRules `trace`, and — when `isUncleanReferral` — an `aiCopilotBrief`.

## Demo walkthrough (Admin UI, :5173)

1. **Simulate & trace highlight** — pick `CASE-04 (Table B referral)` and **Run Simulation**:
   all six nodes of the pipeline light up from the returned trace and the drawer renders the
   stage-by-stage breakdown + AI Copilot card.
2. **Evidence request (Step 1.1)** — run `CASE-09` / `CASE-10`: the sufficiency gate short-circuits
   to `REQUEST_ADDITIONAL_INFO` and the copilot (Mode A) drafts the follow-up explaining why each
   document is needed given the applicant's own metrics.
3. **1-click rule onboarding** — click **Onboard New Rule (Hazardous Occupation Class 4)**, then run
   `CASE-02` under `v2-onboarded-rules`: it escalates `ACCEPT_AS_PER_APPLICATION -> ACCEPT_WITH_LOADING`
   (Table B, +50%) via the new stage-2 rows — no backend code changes.
4. **Excel import** — click **Upload Excel (Decision Table)** and pick `shared/sample-rules-upload.xlsx`:
   the stage-2 table is rebuilt from the spreadsheet and loaded into the visual editor; tweak cells and
   **Save & Hot-Deploy**.

## AI Copilot modes (Requirement 6)

Triggered only when `step4UnderwritingDecision.isUncleanReferral` (CLEAN-path and hard DECLINE
cases bypass the LLM entirely — zero latency, 100% deterministic compliance):

- **Mode A `REQUEST_ADDITIONAL_INFO`** — drafts the agent/customer evidence follow-up from the
  stage-1 missing documents + derived metrics.
- **Mode B `UNCLEAN_RISK_ASSESSMENT`** — synthesizes the interacting stage-2 debits + stage-3
  classification into a disposition recommendation with guideline citations.

Modes are **deterministic/mock by default** (offline, reproducible demos). Set `OPENAI_API_KEY`
(optionally `OPENAI_MODEL`) or `ANTHROPIC_API_KEY` (optionally `ANTHROPIC_MODEL`) for live
structured-output calls; falls back to mock on any error.

## Notes

- **Zen expression constraints discovered in-phase-0** (encoded in the graphs): this
  `@gorules/zen-engine` build has no `pow`/`**` (use explicit multiplication) and no 2-arg
  `round` (use `round(x * 10) / 10`); decision-table result namespacing uses `outputPath`
  + `passThrough` (not `outputField`); `functionNode.content` is `{ "source": "<js>" }`.
- The legacy `if-else` blocks carry machine-readable `// UW_RULE s1|s2|s3 ...` markers that the
  deterministic migrator scrapes; stage rule order must stay in sync with the graph tables.
- `avocations` is an optional input field (default `[]`) added for the onboarded avocation rule.
